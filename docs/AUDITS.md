# OffLeash Music — Audit Log

## 2026-10-27 — 0.7.1-signinfix: the device grant survives leaving the app

**Starting HEAD:** `dde19b78` (0.7.0-google). **Owner field report, verbatim:** "Right as soon as I click out of the app the sign in process restarts." The device-code flow could never complete: approving REQUIRES leaving the app for a browser, and leaving the app restarted the grant — the code he approved at google.com/device belonged to a grant the app had already abandoned.

**Root cause (in 0.7.0's code, precisely).** The pending grant existed only in volatile memory. (1) The issued `DeviceCode` — including the `device_code`, the only handle that can ever be polled — was a LOCAL VARIABLE (`val code`) inside `GoogleSessionManager.runSignIn()`; only the user code / URL / expiry were copied into the in-memory `_phase` StateFlow. (2) The poll loop was `signInJob`, a Job on AppContainer's `sessionScope`: application-scoped, so it survived navigation and activity recreation — but not process death. (3) Nothing was persisted: `GoogleTokenStore` seals only GRANTED tokens; no pending-grant record existed anywhere. So: recomposition and activity recreation were safe in-process (the screen only observes state; `startSignIn()` fired only from button taps) — but when tapping "Open google.com/device" backgrounded OffLeash for Chrome and the system reaped the process, the Job and the `code` local died with it. On relaunch a new container + manager were constructed over an empty token store with `phase = Idle` and no record the grant had ever existed; the owner started over with a NEW code while the code he approved could never be polled by anyone. Secondarily, `startSignIn()` unconditionally cancelled the running job and issued a fresh code on every call, so any restart path burned the previous grant; no resume-the-same-grant path existed at all.

**Fix — the grant becomes durable app-level state (3 commits).**
1. *Sealed pending-grant store:* `StoredPendingGrant` (device code, user code, verification URL, issued/expiry instants, poll interval) in `GooglePendingGrantStore` — the token store's exact custody pattern (AesGcm box, `noBackupFilesDir`, own file `google_pending_grant.bin`). The device code is credential-adjacent (it collects the tokens), so it is sealed with the tokens' care and never logged.
2. *Manager owns the grant:* the record is persisted BEFORE the first poll; the sign-in screen only observes it and never issues implicitly. Polling stays on the manager's app scope and is driven by the record. A new manager restores it in `init`: a live grant is republished and polling resumes automatically (an approval given while the app was dead is collected on relaunch); an expired one is cleared and lands on the plain expired ending with the fresh-start button — no zombie polling. `startSignIn()` resumes a live grant instead of issuing (issuance happens only on an explicit start with none live, or after the live one resolves); every terminal outcome (adopted, declined, expired, cancelled, sign-out) wipes the record; a transient poll transport failure now KEEPS the grant (the code is still good) so checking resumes against the same code. New affordance: `checkNow()` — one immediate poll against the current persisted grant, wired to an "I've approved — check now" button on the waiting screen for devices that throttle background work.
3. *Screen + version:* the check-now button; the screen's doc comment now states the durability plainly. Version: code **15**, name `0.7.1-signinfix` (hunt build `0.7.1-signinfix-hunt1`).

**Tests that pin the bug shut (10 new, all in the app JVM subset):** (a) re-entering sign-in — even an explicit second `startSignIn()` plus a check-now — issues exactly ONE grant and renders the SAME user code/expiry throughout (issuance endpoint hit once, asserted by count); (b) manager/process restart with a persisted unexpired grant: a fresh manager over the same stores republishes the same code with zero new issuance, its resumed polling adopts a scripted approval of the ORIGINAL device code, and the spent record is wiped; (c) a persisted expired grant is cleared at construction, lands on the expired ending, and produces zero issuance and zero polls after a beat (no zombie); (d) check-now polls the persisted grant immediately despite an hour-long poll interval, adopting without a new issuance. Plus the store's custody set (round trip, no plaintext device code in the stored bytes, verified wipe, corruption tolerance, liveness boundary). Local suites on the pushed tree: core **164/164** (unchanged — no core diff), app JVM subset **203/203** (193 + 10 new). CI on head `144eb094`: **"OffLeash — Android" run 40574196021 success, "Push on main" run 40574195752 success** (full Gradle build, Compose UI compile, all tests, live smoke).

**Regression guards:** splash (3.8s, tap-skip, cold-launch-only — a process-death relaunch counting as cold is unchanged behavior), playback ladder, autoplay/sleep timer, the 0.6.6 bars pass, token custody/refresh/revocation — none are in the diff; the cookie safety-net code is untouched. Hunt APK: `OffLeash-Hunt-0.7.1-signinfix-hunt1.apk`, 21,268,856 bytes, SHA-256 `e158c98e18a49f29eecb68224c9b5f3f12da497cd669f9a08a1224f009a3fca2`, signer G3 `3176e075d152787d2f4d5224d26f42ca38a88563abcc3d4a12cb4a17081e84b4` (apksigner-verified). **Remaining proof is the owner's retest:** install → Sign in with Google → note the code → switch to Chrome, take your time, approve → return to the app → signed in, no new code, no restart. ## 2026-10-27 — 0.6.7-pasteformat: the owner's cookies.txt + the window gate's subset rule

**Starting HEAD:** `87234670` (0.6.6). **Owner evidence:** with the paste fallback now reachable, he pasted his cookie export and screenshotted the result (14:22): the failure card above the paste field, and the export visible inside the field — a **Netscape cookies.txt** file (one cookie per line, seven TAB-separated fields, `.youtube.com` rows). The panel underneath the card shows the confirmation sealed in ~2 seconds by "capture unchanged between attempts — stopping at the subset stage" beneath a **0 of 15** subset line — and no per-host counts anywhere.

**Finding 1 — the paste shape 0.6.6 did not read.** The normalizer accepted header strings, a `Cookie:` label, one-pair-per-line, and JSON exports — but the owner's cookie tool (the Get-cookies.txt / yt-dlp shape) writes cookies.txt: domain, flag, path, secure, expiry, name, value, TAB-separated, with `#` comment lines and a `#HttpOnly_` prefix on HttpOnly rows' domains. Read as a header string it yields nothing usable (the first `=` in a row sits inside the seventh field). **Fix:** `SessionCookies.normalizePastedCookie` gains the Netscape shape (new `PastedCookieShape.NETSCAPE_COOKIE_FILE`), tried after JSON and before the header reading: a line counts only at exactly seven TAB-separated fields; `#HttpOnly_` is stripped before the comment check; `#` comments and blank lines are ignored; name is field six, value is field seven whole (`=` inside survives); later rows overwrite earlier ones. A text with no cookie line at all falls through to the header reading, unchanged. The sign-in screen's instructions now name cookies.txt among the accepted shapes.

**Finding 2 — the unchanged-abort keyed on the wrong string.** The 0.6.5 window-honesty fix required the RAW capture to be non-blank before two identical reads could stop the window. The 14:22 panel is the hole in that rule: a raw string can be **non-blank and byte-stable while the session subset inside it is entirely missing** — blank-valued placeholders a store holds mid-landing, non-session cookies riding along, or a pasted text the subset stage cannot read (his cookies.txt, read as a header string, is all three at once) — and the gate fires in ~2s on exactly the failure the window exists to outwait. **Fix:** the early stop now requires session MATERIAL — at least one session cookie carrying a value — AND an unchanged re-read; a capture whose subset is entirely missing always runs the full window, regardless of raw content or stability. Pinned by tests: a subset-present-but-incomplete unchanged capture keeps its early stop; a subset-missing unchanged capture (PREF only) reads every attempt with no "capture unchanged" line; blank-valued placeholders (`SAPISID=; SID=; LOGIN_INFO=`, the synthesized shape of that store state) do not stop the window and a landing on read three converges.

**Why the per-host counts were absent — traced in code.** The counts exist only as a side effect of the WebView harvest provider, logged on each provider call, ahead of the gate — on the WebView path they cannot be skipped. The 14:22 attempt never entered the harvest: its signature is a CONSTANT provider (byte-identical raw, zero subset, immediate unchanged-abort) and the screenshot shows the paste field filled with his export — the attempt was fed by the paste path, which has no harvest to log from. Worse, the paste path's own reading line ("pasted cookie read as …") was logged by the screen BEFORE `completeSignIn` ran, and `completeSignIn` opens with `startAttempt()`, which clears the recorder — the line was erased before the panel could ever render it. **Fix (placement only):** `submitPaste` now logs the reading from INSIDE the provider lambda, so it belongs to the attempt's record on every read, ahead of every stage decision — the paste counterpart of the harvest's counts. The harvest's sources, merge, and logging are untouched.

**Regression guards:** 0.6.4 totality + CrashReporter untouched; the identity parser untouched; 0.6.5 harvest sources unchanged (only gate/logging placement moved); 0.6.6's layout and bars pass untouched (the screen diff is the shape label, the moved log line, and one instruction sentence). Suites: core **143/143** (139 + 4 Netscape) and the app JVM subset **183/183** (180 + gate pair + placeholder + Netscape-adoption) locally via this hunt's own kotlinc harness; CI is the authoritative full build, UI compile included. No dependency changed; the hash lock is untouched; signer and package unchanged.

**Delivered build:** hunt APK from this push's CI (see the 0.6.7 report for size/SHA-256/signer verification). No public release — owner's retest decides. (The owner's screenshotted export is live credential material in a screenshot; the crew did not open or transcribe it — he rotates it out and retests with a FRESH export.)

## 2026-10-27 — 0.6.4-crashfix: sign-in crash hunt — the adoption corridor

**Starting HEAD:** `cd80df91` (0.6.3). **Device evidence:** the owner retested 0.6.3 the same morning — playback confirmed working ("everything is playing correct even BAPHOMET"), but sign-in now CRASHED: email → password → "Yes, it's me" → ~1s of loading → the whole app disappeared. 0.6.2 had failed the same moment politely (diagnostics card); 0.6.3 died. Timing discriminated the stage: not the WebView, not Google's pages — the confirmation execution after successful auth.

**Parser exonerated by reproduction.** The new menu parser was driven against 23 synthetic variants of the endpoint's real structural possibilities (no/several flagged selected, three account sections, brand-only sections, missing serviceEndpoint/photo/header, bare-string names, string-serialized flags, unknown interleaved renderers, non-JSON/empty bodies, XSSI prefix, a 250-deep tree, a 360-identity menu, odd token kinds, unwrapped items): zero escapes, and every identity resolved with the correct semantics (selected item wins; a brand identity shares its account's `authuser`, distinguished by pageId). One premise correction from the harness: kotlinx's `booleanOrNull` reads a string-serialized `"true"` leniently — benign, selection still lands on the flagged identity.

**Root cause — the adoption corridor.** Everything downstream of a confirmed identity was first-run code in 0.6.3: in 0.6.2 the parser never confirmed, so adoption never executed on a device. Adoption's `SessionStore.save` is the first Keystore seal and the first session-file write of the app's life (with no session stored, startup's `load()` returns before the seal is ever touched), and its failure modes — Keystore faults (`KeyPermanentlyInvalidatedException`, provider errors) and file-write `IOException`s — were caught NOWHERE: not in `AesGcmSecretBox.encrypt`, not in `SessionStore.save`, not in `SessionManager.adoptIdentifiedSession`/`completeSignIn`, and not in `SignInScreen`'s `rememberCoroutineScope().launch`, which has no exception handler — so the throw became a process crash. Proven structurally in the hunt harness: the identical confirmation flow over the real client returns Success with a healthy store and ESCAPES `completeSignIn` with a throwing seal or a throwing write. Which of the two threw on the owner's unit is unknowable post-hoc — 0.6.3 kept no crash record (see the capture below); the fixes make both non-fatal AND name the stage if either recurs.

**Fixes, in workstream commits:**
1. *Core identity totality + shape evidence:* the parse step of `accountIdentities` is wrapped (Throwable — a pathological tree failing with an Error degrades the same way), so the lookup's "never throws" contract holds at the boundary, and `IdentityLookup.Found` now carries a `shapeSummary` (top-level keys + section/item counts — names and counts only, never values) that the sign-in diagnostics log on every answer, confirmed or empty. The multi-account menu is a permanent fixture (`derived_account_switcher_multi.json`) with six new variant tests.
2. *Adoption corridor closed:* `SessionManager` catches at the identity call (an unexpected throw fails the attempt at once — it is not a settling problem — logging the `identity` stage), at adoption (logging `sign-in`), and at the save itself (logging the `store` stage with the exception class) → `Failed` with copy that names the real class ("YouTube confirmed your account, but the app couldn't save the session on this device…"). Rollback intact: an unstored confirmation stores nothing. The same seal corridor in cookie rotation (a launched save with no handler) and in `validateNow`'s persistence refresh is wrapped the same way. `SignInScreen`'s launch gained a last-resort guard mapping any escape to the failure card.
3. *Keystore first-generation rescue:* `KeystoreSecretKey.getOrCreate` retries generation once after clearing a possibly half-created entry when the first-ever generation throws — safe precisely because an alias that has never existed has never sealed anything, so nothing can be orphaned. A second failure propagates into fix 2's polite path.
4. *Crash capture:* the app now keeps a persisted last-crash record. `CrashReporter` installs a default uncaught-exception handler from `Application.onCreate` that writes the dying trace (timestamp, thread, full stack — capped, local-only, in the no-backup directory, no new permission, nothing transmitted) and then delegates to the platform's handler. The sign-in screen shows the recorded trace after a relaunch, with a Clear action — so any future failure, crash included, arrives with its stage or its stack attached (fleet debugging ethos: failures must be informative, never fatal).

**Regression guards:** the 0.6.3 workstreams are untouched (autoplay continuation + sleep-timer supremacy, splash spec, polish, window ladder, anonymous playback, music-origin youtubei calls byte-identical — the parser's outputs across all 23 hunt variants are identical before/after this change). Local suites: `:core` 123/123 (117 + 6 new), app JVM logic 201/201 (193 + 3 adoption-corridor + 5 crash-reporter) via the sandbox kotlinc harness; CI is the authoritative full build. No dependency changed; the hash lock is untouched.

## 2026-10-25 — Playback hunt round 3 (Lane B, code): adaptive Range window

**Starting HEAD:** `db3af086` (0.6.1-streamfix + Sweep #5; suites core 116 / app 182 per flavor). **Branch:** `hunt-window` (coordinator integrates; no release).

**The unproven shape element:** round 2 unified probe/player headers, but the Range WINDOW stayed fixed — `RangeInterceptor.STREAM_RANGE_WINDOW_BYTES` = 1 MiB for every normalized fetch — while the only proven on-track wins used tiny windows (`bytes=0-2047`, `bytes=0-0`). **What landed:**
1. **Window descent within one resolution.** The anonymous-road ladder now descends `RangeInterceptor.STREAM_WINDOW_LADDER` — 1 MiB → 256 KiB → 64 KiB → 2 KiB — inside a single (resolve → probe) pair before any re-resolve: a 403 at the current window descends (pure `windowProbeVerdict` in QueueController); a 2xx at any rung wins for that stream and stops the descent; non-403 refusals and transport failures stop the descent and the existing pair verdict (`ladderProbeVerdict`, context rotation, 3 pairs) decides as before. 2. **Winner handoff by construction.** A new shared `StreamWindowStore` (one instance in AppContainer) maps stream URL → window. The probe presets NO header (the pinned probe shape is unchanged — `PlayerFetchShapeContractTest` passes unmodified): before each probe fetch the ladder records the CANDIDATE window for that URL in the store, and `RangeInterceptor` — the one shaping point for probe, player, and test fetch alike — normalizes the fetch with the recorded window. The winner travels out of the ladder in the new `ResolvedPlayback(info, windowBytes)` type, and `QueueController.handToPlayer` re-records it into the store BEFORE `player.setMediaItem`, so the player's first load of that exact URL is shaped with the winning window. Loads stay bounded by construction (absent → bounded at the per-stream window; open-ended → bounded at it; already bounded → untouched). Account-road streams are never probed and ride the default 1 MiB, as before. Downloads are untouched: `OkHttpChunkFetcher.probeTotalBytes` keeps its `bytes=0-0` preset and `fetchRange` its bounded presets (both pass the interceptor untouched).

Formats are pure functions (`streamLoadLine`, `probeWindowLine`, `winningWindowLine`, `rangeOffsetAndWindow`), pinned by tests.

| | Ladder probe | Player first fetch |
|---|---|---|
| Range | `bytes=0-0` (preset by probeUrl) | none set by OkHttpDataSource for DataSpec(0, LENGTH_UNSET) (`HttpUtil.buildRangeRequestHeader` returns null) → RangeInterceptor's `bytes=0-1048575` |

The diagnostics test-fetch shared the probe's UA/AE shape but the player's range window, on a different URL instance — consistent with the refusal tracking the request, not the track. Downloads, notably, always rode the probe's shape (OkHttpChunkFetcher presets bounded ranges on the shared client, no UA of its own) and were never reported broken.

**Bisect (afd47684 → 8bf0baf8).** The fetch stack did NOT change: `buildPlayer`'s data-source chain and `RangeInterceptor` are byte-identical across the whole window; the shared client's construction moved from `OffleashApp` into `buildSharedClient` (Lane B, `872cdb9f`) with identical parameters; Media3 stayed 1.5.1, OkHttp 4.12.0. ## 2026-10-23 — Background playback fix (screen-off stops after ~5 seconds)

**Owner's on-device verdict (2026-10-23 20:40 CDT):** the hunt1 build PLAYS on the owner's phone (moto g stylus 2025) — "I've got music playing and everything is working great." **Diagnosis (code-level, coordinator-verified at base `afd47684f3fa`):** the media session was never registered with `PlaybackService` — `PlaybackService.onCreate` built a `MediaSession` but never called `addSession(...)`, and no `MediaController`/`SessionToken` existed anywhere in the app (the UI drives the shared ExoPlayer directly via `QueueController`). The manifest declarations were correct and ExoPlayer wake mode was `C.WAKE_MODE_NETWORK`. The ~5 seconds is the `startForegroundService` contract window: screen-on, the resumed activity keeps the process important; screen-off, a started, non-foreground, session-less service is reaped and playback dies as the buffer drains. Latent extra: `QueueController.ensureServiceStarted()` had a one-shot `serviceStarted` latch — after `onTaskRemoved` stopped the service while paused, no later play in the same process ever restarted it. OEM half: even a correct foreground-service app can be killed when battery-restricted on Motorola, addressed by the detection card (fix E).

**Fixes (A–H):**
- **A.** `PlaybackService`: `addSession(mediaSession)` after building the session; service lifecycle recorded into `PlaybackDiagnostics` (`recordServiceRunning`, running on create / not running on destroy) via the container's shared recorder. `onTaskRemoved` semantics unchanged.
- **B.** `AppContainer`: a process-lifetime `MediaController` connected to the PlaybackService `SessionToken`, built async with try/catch; failure only logs into diagnostics. `QueueController` still drives the player directly — transport was NOT rerouted through the controller.

## 2026-10-23 — Playback hunt (on-device failure)

**Trigger:** on the owner's phone, Phase 1 browses and queues, then playback fails with a toast reading only "Something went wrong playing this track. Try again." Resolution had succeeded; Media3 failed after the hand-off.

**The defect:** `QueueController.onPlayerError` was a generic catch-all that discarded the `PlaybackException` entirely — no error code, no HTTP status, no cause. That is a SPEC §6 taxonomy hole: the player stage had no named errors at all, so a diagnosable server refusal surfaced as a content-free toast and left nothing to act on. Fixed on branch `hunt-playback`: `ErrorMessages.playerMessage(errorCode, httpStatus)` now names every player-stage shape (see SPEC §6 player rows), the fallback still names the numeric error code, an HTTP 403 triggers exactly one re-resolve-and-retry for the same track, and a Playback diagnostics recorder + screen (About → Playback diagnostics, with a Test playback probe track) records the last attempt stage by stage.

**Probe evidence (agent-side, before the fix):**
- Fuller coordinator probe (owner's track, videoId `lY5V4hSLWY8`, fresh resolution, **both itag 251 and itag 140, both `gir=yes`**):

  | Request shape | Result |
  |---|---|
  | GET with **no Range header** | **HTTP 403** (deterministic, repeated) |
  | GET with `Range: bytes=0-` (**open-ended**) | **HTTP 403** |
  | GET with `Range: bytes=0-2047` (**bounded**) | **206** |
  | GET with a **bounded mid-file range** | **206** |

  The server requires a **bounded** range (an explicit end byte). This corrects the first probe's summary ("any Range form → 206" — an open-ended range does *not* pass) and its note on itag 140: with a fresh `gir=yes` URL, itag 140 is refused in the same shapes as 251.
- Media3's data sources produce exactly the refused shapes: no Range header when position is 0 and length is unset (`HttpUtil.buildRangeRequestHeader` returns null), and an open-ended `bytes=N-` when a length is unset at a non-zero position — so the player's fetches were refused by shape, not by content.
- Every prior smoke always sent a bounded Range explicitly; the range-less and open-ended seams were never exercised. The live smoke now also probes a range-less GET and an open-ended GET informationally (non-gating; see SPEC §8).
- Both stream URLs embed an `ip=` param: googlevideo binds streams to the resolver's egress identity, so resolver/player stack divergence is a real risk, not a theory.
- UA is **not** the gate: no-UA and foreign-UA fetches return 206 when the range is bounded.

**Hypotheses verdicts:**
- **H1 — resolver/player stack divergence (OkHttp vs HttpURLConnection, address-family choices on an IPv6-first carrier): plausible-contributor.** Fixed by alignment: stream fetches now go through the shared OkHttp stack (`media3-datasource-okhttp`, `CacheDataSource → OkHttpDataSource` on the shared client) — the same stack that resolved the URLs fetches them.
- **H2 — User-Agent mismatch is the gate: refuted.** No-UA and foreign-UA bounded-range fetches return 206 (see probe evidence above).
- **H3 — replay-cache interference: not indicated.** The upstream failure is cold-cache-shaped, and the cache factory sets `FLAG_IGNORE_CACHE_ON_ERROR` — the cache falls back to the network source on its own errors and is never a gate.
- **H4 — resolver/browse failure misreported as a player failure: refuted.** The toast string existed only in `QueueController.onPlayerError`; its provenance proves resolution succeeded and the failure was post-hand-off, in the player.
- **H5 — the player's first fetch shape (range-less or open-ended) is refused; bounded ranges required: PROVEN agent-side.** Deterministic on the owner's exact track, both itags (above): no-Range → 403, open-ended `bytes=0-` → 403, bounded → 206. An earlier draft of this hunt briefed a "add `bytes=0-` when absent" interceptor — that would **not** have fixed the phone, and the coordinator's fuller probe caught it before merge. Fixed instead by a scoped OkHttp application interceptor (`RangeInterceptor`, a range *normalizer*) on GET requests to `*.googlevideo.com` hosts only — never on youtubei POSTs, never on other hosts: no Range → `bytes=0-1048575` (1 MiB window, `STREAM_RANGE_WINDOW_BYTES`); open-ended `bytes=N-` → `bytes=N-(N+1048575)`; already bounded → untouched. Its normalization and scoping are unit-tested exactly (absent→bounded-from-0, open-ended→bounded preserving start, bounded→unchanged, POST untouched, non-googlevideo untouched).

**Remaining proof:** the on-device verdict is still the owner's — the hunt build (`hunt` flavor, applicationId `dev.cyberdogs.offleash.hunt`, label "OffLeash Hunt") plus the diagnostics screenshot from a failed or successful attempt on his phone and network. No agent-side result substitutes for that.
